# Planned future upgrades

Ideas that are worth doing, with the measurement that justifies each and an
honest estimate of what it buys. Nothing here is committed work — the point of
the file is that a future session can pick one up *and know why*, or drop it
knowing what it would have cost.

Ordered by expected value, best first.

---

## 1. A distillation corpus for Qwen3, and the draft model trained on it

**Status: worth doing, but it is not the cheap win it looks like, and the
measurements below should be read before starting.**

This is `speculative-decoding-plan.md`'s Phase 1, respecified. The plan says to
train the draft on "a general web text or instruction-style corpus". That is the
wrong objective: the draft's usefulness is measured entirely by *acceptance rate
against Qwen3-0.6B*, so the training objective should be agreement with Qwen3,
not fluency in general. Sequence-level knowledge distillation (Kim & Rush 2016)
applied to speculative decoding is DistillSpec (Zhou et al. 2023), and it
reliably beats corpus pretraining at the same budget for exactly this reason.

**The corpus** is therefore Qwen3-0.6B's own greedy (or low-temperature)
continuations of a prompt set, generated by this engine, and the draft is trained
to reproduce them token for token.

### Why it is the only route to the one thing the engine cannot currently do

The n-gram proposer that ships today wins ~1.8x on text that repeats itself and
loses ~5% on open-ended generation, where the last few tokens have never occurred
before and there is nothing to look up. **A trained draft is the only proposer
that can help open-ended generation.** That is a real gap and a real reason to
do this.

### Why it is harder here than the plan assumes

Three measured obstacles, none of which the plan anticipated:

**a. The vocabulary, not the body, sets the draft's cost floor.** Qwen3's
vocabulary is 151,936 tokens. At any sane hidden size the embedding and LM head
dominate a small draft, and the LM head GEMM runs on *every* draft step. The
evidence is in `benchmark/results/spec_sweep.json`: the 42M random draft costs
~1.8 ms per proposal step against the 0.6B target's ~8.7 ms decode step. A model
14x smaller is only ~4.8x cheaper, and shrinking the body further will not close
that — the fixed vocabulary cost is already most of it. This is why break-even
for the draft path sits at ~60% acceptance at K=4 and will not move much.

**b. The acceptance ceiling is known and it is not enough on its own.** The
sweep includes the target drafting for *itself* — 97-99% acceptance, the
absolute upper bound any trained draft can approach. On open-ended prompts it
still runs at **0.85-0.90x of plain decode**, because a 0.6B draft is not cheap.
A trained 42M draft would have the *random* draft's cost curve (K=4: 94 tok/s at
0% acceptance, against a 200 tok/s baseline) and, optimistically, 60-80%
acceptance. Interpolating those two measured endpoints puts the realistic landing
zone at **1.1-1.5x on open-ended text at K=2-4** — real, but not the 2-3x the
technique is known for on 7B+ models.

**c. Generating the corpus is the expensive part, not training.** A 42M model is
Chinchilla-optimal at roughly 800M tokens. Generating that many tokens of Qwen3
output on this RTX 3050 is the bottleneck: even at a batched ~1500 tok/s it is
~6 days of continuous generation, and this engine's own throughput work is what
would have to make that number real. Training the draft afterwards is
comparatively cheap. Budget the corpus, not the optimiser.

### If it is done anyway, do it in sprints

The dominant risk is "does acceptance clear ~60%", which a 10M-token pilot
answers in an afternoon. It is *not* "will it converge". So:

1. 10M tokens, tiny draft, measure acceptance against the target. Stop here if
   it is far below 50% — the rest will not rescue it.
2. 100M tokens, measure again, and fit the trend.
3. Only then commit to the full run.

Gate each sprint with `experiments/spec_breakeven.py --method draft`, which
converts an acceptance rate into a speedup without needing a full sweep.

### What would change the calculus

- **A smaller vocabulary.** A draft restricted to the top ~32k Qwen3 tokens,
  with the rest mapped to a rejected sentinel, would cut the LM head by ~5x. It
  breaks the "same vocabulary" assumption `Config` asserts, and rejection
  sampling needs `q` over the target's full vocabulary — so it needs care, but
  it attacks obstacle (a) directly and is the highest-leverage variation.
- **A bigger target.** Every obstacle above is a consequence of the target being
  only 0.6B. On a 7B target the fixed overheads that dominate here vanish, and
  the standard results apply.

## 2. Lift the batch-width ceiling on byte-identical output

`experiments/kv_shape_drift.py` measures it: above a verify-pass batch width of
14 on this host, the projection GEMM retiles and writes **different K/V into the
paged cache** than a decode step would. That is permanent, so the speculative
and plain runs stop decoding over the same numbers and diverge later, at a step
that need not be a near-tie.

Output is still *correct* above that width — rejection sampling remains exactly
distribution-preserving, so it is a valid sample from the target — but it is no
longer the *same* sample plain decoding would have produced, so the byte-identity
gate cannot be used there.

Since width is `num_requests * (K+1)`, the ceiling binds hard as concurrency
grows: at 2 concurrent requests K must stay <= 6, and at 8 concurrent requests
there is no usable K at all. Worth attacking if speculative decoding is ever
wanted at real batch sizes. Likely approaches: pin a cuBLAS algorithm for the
projection, pad the verify pass to a fixed width so decode and verify share a
shape, or accept the drift and replace the byte-identity gate with a
distributional one.

## 3. Speculative decoding with top-k / top-p

Currently asserted greedy-only. Rejection sampling has to compare against the
exact distribution the non-speculative path would have sampled from, and for
top-k/top-p that lives inside flashinfer's fused kernel and is never exposed.
Fixing it means reimplementing the truncation in a form that returns
probabilities, then feeding those to `rejection_sample` unchanged — the sampler
itself already handles arbitrary distributions and is tested against them.

## 4. Prefix caching together with speculative decoding

Asserted incompatible today. A multi-token commit can step over the block
boundary `cache_block_if_needed` hashes on, leaving a gap in the prefix chain.
The fix is to hash every block boundary the commit crossed rather than only the
one it landed on. Small, and currently blocked on nothing but someone wanting it.
